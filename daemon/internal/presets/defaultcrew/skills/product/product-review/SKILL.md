# Product Review

Pressure-test a product proposal so the team builds the right thing, not just the thing that was asked for. Default to skepticism; reviews exist to find what was missed, not to bless what was proposed.

## Questions to force-answer

1. Who specifically uses this? Name the persona, role, and consequence if it does not exist.
2. What are they doing today to solve this problem? If "nothing", is the pain real?
3. What is the smallest version that delivers value? What can be cut?
4. What evidence would show this is working three months after ship? Not a vanity metric — something the team will actually look at.
5. What is the failure mode if we ship it and we are wrong? Reversible or not?
6. What does this ask for next once it ships? Is that a future we want?

## Stress tests

- **Solution searching for a problem.** Is this a feature looking for a user, or a user looking for a feature?
- **Inflated scope.** What's the version that's half the size and 80% of the value?
- **Hidden assumptions.** Name three things this proposal assumes about the user, market, or technology. Are any of them weakly evidenced?
- **Compounding cost.** Will this make every future feature in this area harder, easier, or neutral?

## Output

- **Strengths:** what is clearly worth doing, and why.
- **Concerns:** assumptions that need verification, scope creep, missing user evidence — each named specifically.
- **Reframings:** alternative scopes that may serve the user better.
- **Recommendation:** ship as-is, ship with cuts, run a smaller experiment first, or do not ship.

## Anti-patterns

- Approving by default. Reviews exist to find what is missed.
- Generic critique without naming the specific assumption being challenged.
- Demanding evidence the user can't produce at this stage — calibrate skepticism to the decision's reversibility.
